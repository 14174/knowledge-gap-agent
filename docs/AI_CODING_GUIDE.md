# AI Coding 工程规范

## 1. 目的

本规范用于让新的协作者或新的 Codex 会话在不依赖历史对话的情况下继续开发，并保证新增代码、数据、实验和学习材料仍属于同一个项目。

项目的一致性来自四条主线：

1. 同一组模块边界。
2. 同一套可复现数据契约。
3. 同一条测试、审查和人工门禁链路。
4. 同一份仓库内长期记忆。

根目录 [AGENTS.md](../AGENTS.md) 保存必须自动执行的短规则；本文解释具体做法和交接标准。

## 2. 新会话接手流程

Codex 接到任务后先建立事实基线，不直接编辑文件。

### 2.1 读取顺序

```text
AGENTS.md
  ↓
docs/TODO.md
  ↓
相关设计书与实施计划
  ↓
docs/decisions.md
  ↓
目标源码与相邻测试
  ↓
git status / git log / 当前分支
```

只读取与当前任务有关的设计资料。不要把整个 `docs/` 目录一次性塞进上下文，也不要把聊天摘要当作最终事实。

### 2.2 建立基线

```powershell
git status --short
git branch --show-current
git log -5 --oneline
uv sync --extra dev
uv run python -m pytest -q
```

若 `uv run pytest` 意外加载系统环境，改用 `uv run python -m pytest` 并检查解释器路径。基线失败时先定位根因；没有用户确认，不得把已有失败归入当前任务后继续开发。

### 2.3 确定授权边界

将请求归入以下一种类型：

| 类型 | 允许动作 |
| --- | --- |
| 解释、审查、诊断 | 读取、运行只读检查、报告证据；不修改代码 |
| 设计 | 编写设计书和决策记录；获得确认前不实现 |
| 实现 | 按已确认设计修改代码、测试和相关文档 |
| 实验 | 运行已冻结配置，保存真实结果和环境信息 |
| 发布 | 在全量验证和人工门禁通过后合并、推送或打标签 |

用户说“继续”表示沿当前已确认计划推进，不表示可以跨过人工审核、发布或外部写入门禁。

## 3. 项目模块地图

当前已落地模块与计划模块必须沿同一方向生长。

| 路径 | 当前职责 | 不应承担 |
| --- | --- | --- |
| `src/knowledge_gap_agent/contracts/` | 运行配置、Trace、Benchmark 等稳定数据契约 | 文件读写、检索、Agent 执行 |
| `src/knowledge_gap_agent/utils/` | 与业务无关的规范 JSON 和哈希工具 | 业务字段判断 |
| `src/knowledge_gap_agent/corpus/` | 来源清单、文本规范化、Markdown 切块、Claim 与证据 | 排名、搜索决策、模型调用 |
| `src/knowledge_gap_agent/retrieval/` | 确定性分词、BM25 排序和分数解释 | Sufficiency 判断、联网搜索 |
| `src/knowledge_gap_agent/benchmark/` | 知识环境、数据校验、独立复核、人工门禁、冻结 | Runtime 执行和答案生成 |
| `demo/` | 可重复运行的单一能力演示 | 隐式网络调用、随机模型输出 |
| `fixtures/` | 固定来源、语料、基准与审计记录 | 无来源的手填结果 |
| `learning/` | 从代码、公式和 Demo 派生的渐进课程 | 未实现功能的概念堆砌 |

后续 `runtime/`、`knowledge/`、`tracing/`、`eval/` 和 `skills/` 按 `README.md` 与项目计划增量落地。不要提前创建空包，也不要为了“完整架构”一次性生成骨架。

## 4. 稳定契约

### 4.1 规范 JSON 与哈希

身份哈希统一使用 `utils/canonical.py` 的规范 JSON：

- 映射键排序。
- UTF-8 编码。
- 禁止 `NaN` 和无穷大。
- 不依赖对象创建顺序。

新增哈希前先回答：它标识的是内容、环境、配置还是结果。不同身份不得复用同一字段名来表达。

### 4.2 冻结模型

跨模块和落盘前的数据模型使用 Pydantic：

- `frozen=True`。
- `extra="forbid"`。
- 新增稳定字段时升级 `schema_version`。
- 集合字段内部使用 `tuple`，JSON 模式输出数组。
- 公共入口重新验证传入实例，不能信任 `model_construct()` 或不校验的复制结果。

不要实现“不可变 `list` 子类”。Python 基类方法可以绕过实例方法覆盖，也容易破坏深复制和 Pickle。

### 4.3 语料来源

外部文档必须记录：

- 仓库与来源网址。
- 40 位提交 SHA。
- 相对路径。
- 抓取时间。
- 规范化内容哈希。
- 引用行范围。

清单路径统一使用 POSIX `/`。禁止浮动分支、路径逃逸、Windows 设备名、控制字符和跨平台含义不同的路径字符。

### 4.4 运行、标签与审计隔离

```text
runtime.jsonl               → 评测器关联信封，可保留样本、基础问题、环境和可见块编号
build_model_input_payload() → 决策模型输入，只含问题和按环境顺序解析的可见知识正文
labels.jsonl                → 评测器读取的真值
audit.jsonl                 → 来源、复核、人工结论和构造记录
```

冻结运行文件是评测器信封，不得原样传给决策模型。评测器先用其中的编号关联环境和语料，再调用独立字段白名单构造模型输入；模型不得接收任何样本、基础问题、环境或块编号，也不得接收类别、研究决策、必需或缺失主张等标签信息。模型输入公共入口先通过 `model_validate(model_dump(mode="python"))` 重验 case、environment 和每个 chunk，再校验 case 与 environment 配对，禁止不校验的复制对象绕过哈希和必填字段约束。两层载荷都不得采用“先序列化完整对象再删除几个字段”的黑名单方式。新增 Benchmark 字段时必须检查 `LABEL_FIELDS`、冻结输出、模型输入白名单和泄漏测试。

## 5. 开发流程

### 5.1 设计门禁

出现以下任一变化，先写设计或决策记录：

- 新模块或模块职责变化。
- 公共类型、状态机或落盘格式变化。
- 新的数据流或外部依赖。
- 实验变量、指标或人工门禁变化。

小型缺陷修复不需要重写设计书，但应在测试中固定正确行为；若修复改变既有契约，更新 `docs/decisions.md`。

### 5.2 TDD 循环

每个行为按以下顺序完成：

1. 写一个只表达目标行为的测试。
2. 运行目标测试，确认它因功能缺失而失败。
3. 写最少生产代码。
4. 运行目标测试和相邻回归。
5. 必要时重构，保持绿灯。
6. 运行全量测试后提交。

测试不得调用生产公式生成预期值。BM25、哈希和指标需要独立手算值或固定金丝雀常量。

### 5.3 两级审查

每个独立任务按固定顺序审查：

1. **规格审查：** 是否少做、多做或改变了已确认契约。
2. **代码质量审查：** 正确性、边界、可维护性、跨平台性和测试盲点。

审查者不修改实现。发现问题后由原实现者补失败测试、修复，再由原审查者复审。不能用实现者自审代替正式审查。

### 5.4 提交

一个提交只包含一个可验证目的：

```text
feat(语料): 添加确定性 Markdown 切块
feat(检索): 实现可解释 BM25 基线
fix(基准): 阻止标签字段进入运行载荷
docs: 记录冻结集合类型决策
test(基准): 覆盖人工升级状态边界
```

提交前运行目标测试、全量测试和 `git diff --check`。不要把工作树中的无关改动一并加入暂存区。

## 6. 测试策略

### 6.1 测试分层

| 层级 | 目标 | 示例 |
| --- | --- | --- |
| 单元测试 | 一个函数或模型的行为 | 分词、哈希、字段校验 |
| 契约测试 | 跨模块稳定输入输出 | JSON 数组、模式版本、状态映射 |
| 数据测试 | 固定数据的引用与分布 | 48 条样本、证据存在、无泄漏 |
| Demo 测试 | 用户可运行路径 | 子进程运行、严格 JSON、重复输出一致 |
| 回归测试 | 固定已发现缺陷 | 围栏伪标题、终止换行、路径 NUL |

### 6.2 必测边界

- 空输入、重复编号、未知引用、越界数值。
- `NaN`、正负无穷大、布尔值冒充整数或浮点数。
- LF、CRLF、终止换行和 Unicode 非基本平面字符。
- 输入顺序置换后的结果与错误顺序。
- `model_construct()`、`model_copy()` 等绕过常规校验的入口。
- Windows 与 POSIX 路径差异。
- 文件写入在第 1、2、3 个阶段失败后的回滚。

### 6.3 验证命令

```powershell
# 单个文件
uv run python -m pytest tests/benchmark/test_review.py -v

# 模块回归
uv run python -m pytest tests/benchmark -q

# 全量回归
uv run python -m pytest -q

# 依赖与差异
uv lock --check
git diff --check
git status --short
```

## 7. Benchmark 与人工门禁

基准构造链路固定为：

```text
结构化草稿
  ↓ 确定性规则校验
validated case
  ↓ 独立 Reviewer Agent
review record
  ↓ 人工升级规则
人工终审或抽检
  ↓
正式冻结
```

约束如下：

- Reviewer Agent 不读取 Labeler Agent 的长推理文本。
- Reviewer 只读取显式白名单生成的结构化草稿、环境三池正文、主张与证据；输入不得包含 `annotation_reason`、`review_status` 或 `human_review_status`。
- `ReviewRecord.review_target_hash` 必须精确绑定 Reviewer 实际可见输入。唯一计算链路是：由 case、environment、chunks、claims 构造无哈希白名单 `ReviewTargetInput`，对其规范 JSON 求哈希，再生成 `ReviewInput`；禁止另写一套仅哈希编号的投影。
- `ReviewInput` 必须在模型级复算并校验自身哈希，使 Python 构造、字典解析和 JSON 解析具有同一拒绝行为。`model_copy` 不验证，公共入口必须通过 `model_dump(mode="python")` 后重新校验。
- case 投影排除 `annotation_reason`、`review_status`、`human_review_status`；环境三池展开后的块正文、来源、标题路径、`claim_ids`，以及相关主张的陈述、时效、冲突边和证据映射全部进入哈希。三个排除字段变化不改变哈希，其余 Reviewer 可见内容变化必须重新复核。
- case、environment、chunk、claim 的字段纳入与排除集合必须显式声明并在生产入口核对；数据模型新增字段时，未先决定 Reviewer 可见性的构建必须早拒绝。
- `evidence_refs` 允许引用对应环境可见、研究、排除三池的并集，不得引用环境外块。复核门禁和冻结均用可信 chunks/claims 重建目标与允许集合。
- `draft_status` 未达到 `validated` 时，不得进入模型复核。
- 复核状态只允许从 `pending` 转换一次；修订产生新记录，不覆盖旧结论。
- 版本化 `change_log.jsonl` 只能通过受审提交或人工流程初始化与追加；确定性构建器只能在写其他产物前只读校验固定前缀和规范追加行，缺失或空文件必须早拒绝。
- 已归档复核的 `prompt_hash` 必须由对应提示词文件原始字节现场计算并与复核、审计记录交叉核对，不能只信任源码常量或记录自报。
- 过时、冲突、低置信度、`revise`、`reject` 和历史规则失败样本必须进入人工审核。
- 人工 `rejected` 的样本不能进入候选或正式冻结集。
- 正式冻结重新计算门禁，不信任调用方手填的状态字段。
- 应用复核门禁和冻结前都用当前可信语料重新验证目标哈希；错误哈希不得冻结。

搜索是否必要只是一个标签，不是 Harness 有效性的最终证据。实验还要报告任务结果、缺口识别、成本和轨迹指标。

## 8. 文档同步矩阵

| 变更 | 必须同步 |
| --- | --- |
| 任务完成或范围变化 | `docs/TODO.md` |
| 公共契约、状态机或关键取舍 | `docs/decisions.md` 和相关设计书 |
| 模块职责变化 | 架构文档、模块索引、本文模块地图 |
| 新实验或数据版本 | `docs/experiments.md`、实验合同、数据哈希 |
| 新的实际缺陷 | 回归测试；需要长期提醒时写 `docs/pitfalls.md` |
| 新 Demo 或课程阶段 | `learning/` 的 GUIDE、LAB、EXERCISES、SOLUTIONS |

不要为了满足矩阵创建空文档。第一次有真实实验时再创建 `docs/experiments.md`；第一次出现值得长期保留的失败模式时再创建 `docs/pitfalls.md`。

## 9. Codex 协作方式

### 9.1 主任务与子任务

主 Codex 负责：

- 维护设计、计划和任务顺序。
- 给实现者提供完整且有边界的任务文本。
- 收集红灯、绿灯和提交证据。
- 安排规格审查和质量审查。
- 决定是否可以进入下一个任务。

子任务一次只承担一种角色：实现、规格审查或质量审查。多个实现任务若修改相同文件，不得并行。

### 9.2 低成本模型的适用范围

可把接口明确、文件较少、测试期望完整的机械任务交给成本较低的模型。架构、数据标签、实验设计和最终审查使用能力更强的模型。无论使用哪个模型，测试与审查门禁不降低。

### 9.3 不依赖隐藏上下文

分派任务必须明确写出：

- 工作树绝对路径和分支。
- 允许修改的文件。
- 接口、约束和非目标。
- 红灯与绿灯命令。
- 是否允许提交。
- 完成报告格式。

不要只发送“继续任务 6”或要求子任务自己从长对话猜测目标。

## 11. 合并与发布检查清单

合并或推送前逐项确认：

- [ ] 设计和实际实现一致。
- [ ] 所有新行为有先失败的测试。
- [ ] 规格审查与质量审查均通过。
- [ ] `uv lock --check` 通过。
- [ ] 全量测试通过，并解释所有跳过项。
- [ ] Demo 实际运行且输出可解析。
- [ ] 数据哈希、条数、来源和人工状态可追溯。
- [ ] `git diff --check` 无错误。
- [ ] 工作区没有无关差异。
- [ ] `TODO`、决策、实验和课程文档按变更同步。
- [ ] 未经明确授权，不创建标签、不推送、不覆盖远端状态。

## 12. 常见割裂信号

出现以下情况时停止实现，先校正上下文：

- 新模块复制了已有哈希、校验或状态机逻辑。
- 同一概念出现两个字段名或两个模式版本。
- Demo 自己实现一套与生产代码不同的算法。
- 测试根据当前实现动态计算预期值。
- 文档宣称的状态与 `TODO`、代码或数据不一致。
- 为了让测试通过而放宽契约，而不是修正失效夹具。
- 模型复核结果被写成人工结论。
- 新会话只看最近聊天，没有读取仓库内设计和决策。

这些信号通常不是局部格式问题，而是项目开始分叉。先回到稳定契约和仓库内事实，再继续编码。
