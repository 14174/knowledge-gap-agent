# 第二天语料、检索基线与基准数据设计

## 1. 目标与边界

第二天交付一套可复现的小型语料、48 条知识环境基准、可解释的 BM25 检索 Demo，以及独立复核流程。它为后续 Runtime、Sufficiency Gate 和消融实验提供固定输入，但不在本阶段实现 Agent Runtime、联网搜索或知识写回。

本阶段回答三个工程问题：

1. Agent 在执行前能看到哪些知识，缺少哪些关键主张。
2. 给定查询时，本地检索能否返回支持答案的证据块。
3. 基准标签是否经过独立复核，且构造信息不会泄漏给运行时。

## 2. 设计原则

- **单一证据池**：语料只维护一份，通过可见、可检索、排除三组块编号组合出不同环境，避免复制 48 套知识库。
- **先规则后模型**：确定性校验负责结构、引用和泄漏检查；模型只处理语义判断。
- **标注与复核隔离**：复核 Agent 不读取标注 Agent 的推理文本，只读取样本、证据和结构化草稿。
- **运行数据与审计数据分离**：冻结样本不携带正确答案所需的审计字段，评测器通过独立文件读取标签。
- **内容寻址**：来源、语料块、环境和冻结数据均计算稳定哈希；JSON 序列化必须按键排序。

## 3. 模块划分

### 3.1 语料模块

目录：`src/knowledge_gap_agent/corpus/`

| 文件 | 职责 | 主要接口 |
| --- | --- | --- |
| `models.py` | 定义来源文档、语料块和知识主张 | `SourceDocument`、`CorpusChunk`、`Claim` |
| `normalize.py` | 统一换行、空白和稳定 JSON 序列化 | `normalize_text()`、`canonical_json()`、`content_hash()` |
| `chunking.py` | 按 Markdown 标题和行范围切块 | `chunk_markdown(document)` |
| `manifest.py` | 读取并校验来源清单 | `load_source_manifest(path)`、`verify_sources(...)` |

`chunk_markdown` 不按固定字符数硬切。每块保留标题路径和原始行号；单节过长时，才按段落边界继续切分。相同输入必须得到相同块编号与哈希。

### 3.2 检索模块

目录：`src/knowledge_gap_agent/retrieval/`

| 文件 | 职责 | 主要接口 |
| --- | --- | --- |
| `tokenizer.py` | 生成确定性中文二元字组和英文词项 | `tokenize(text)` |
| `bm25.py` | 建立内存索引、排序并解释得分 | `BM25Index.build(chunks)`、`search(query, top_k)` |

分词规则：中文连续文本生成二元字组；英文标识符和数字作为完整词项保留；英文字母统一为小写。标点与纯空白不进入词项。该规则追求可复现和便于手算，不承担通用中文分词能力。

BM25 参数固定为 `k1 = 1.5`、`b = 0.75`。对查询词项 `t` 与文档 `d`：

\[
\operatorname{idf}(t)=\ln\left(1+\frac{N-n_t+0.5}{n_t+0.5}\right)
\]

\[
\operatorname{score}(q,d)=\sum_{t\in q}\operatorname{idf}(t)
\frac{f(t,d)(k_1+1)}{f(t,d)+k_1\left(1-b+b\frac{|d|}{\operatorname{avgdl}}\right)}
\]

搜索结果返回总分和逐词项贡献，排序键为 `(-score, chunk_id)`，以消除同分时的不确定性。

### 3.3 基准构造模块

目录：`src/knowledge_gap_agent/benchmark/`

| 文件 | 职责 | 主要接口 |
| --- | --- | --- |
| `draft.py` | 由基础问题和环境模板生成结构化草稿 | `build_drafts(...)` |
| `review.py` | 解析独立复核结果并执行人工升级规则 | `review_case(...)`、`requires_human_review(...)` |
| `validation.py` | 校验覆盖、引用、环境互斥和答案泄漏 | `validate_case(...)`、`validate_dataset(...)` |
| `freeze.py` | 生成运行集、标签集、审计清单和数据哈希 | `freeze_benchmark(...)` |

基准由约 12 至 16 个基础问题派生为 48 个知识环境。派生改变可见证据、可检索证据、冲突证据或时效条件，不用同义改写凑数量。基础问题之间应覆盖配置稳定性、错误诊断、知识充分性、检索决策、冲突与过时知识等项目核心场景。

## 4. 数据模型与接口

以下类型采用项目现有的 Pydantic 约束风格。字段名为稳定外部契约，新增字段需要同步更新数据版本。

```python
class SourceDocument(BaseModel):
    source_id: str
    title: str
    source_url: str
    repository: str
    commit_sha: str
    relative_path: str
    fetched_at: datetime
    content_hash: str
    content: str


class CorpusChunk(BaseModel):
    chunk_id: str
    source_id: str
    heading_path: tuple[str, ...]
    start_line: int
    end_line: int
    text: str
    token_terms: tuple[str, ...]
    content_hash: str
    claim_ids: tuple[str, ...]


class Claim(BaseModel):
    claim_id: str
    statement: str
    evidence_chunk_ids: tuple[str, ...]
    valid_from: datetime | None
    valid_until: datetime | None
    conflicts_with: tuple[str, ...]


class KnowledgeEnvironment(BaseModel):
    environment_id: str
    visible_chunk_ids: tuple[str, ...]
    research_chunk_ids: tuple[str, ...]
    excluded_chunk_ids: tuple[str, ...]
    environment_hash: str
```

现有 `BenchmarkCase` 增加以下字段：

```python
base_question_id: str
environment_id: str
required_claim_ids: tuple[str, ...]
missing_claim_ids: tuple[str, ...]
evidence_chunk_ids: tuple[str, ...]
draft_status: Literal["generated", "validated"]
review_status: Literal["pending", "approved", "revise", "rejected"]
human_review_status: Literal["not_required", "pending", "approved", "rejected"]
```

冻结时拆成三类文件：

- 运行集：供评测器关联问题、环境与可见块的信封；允许保留关联编号，但不能原样传给决策模型。
- 标签集：目标决策、必需主张、缺失主张和证据引用，仅供评测器读取。
- 审计集：来源、生成配置、复核意见、人工结论和变更历史。

评测器根据运行信封解析环境与语料后，必须通过独立白名单构造决策模型输入。模型输入只含问题与按环境可见顺序排列的知识正文，不含样本、基础问题、环境、块编号，也不含类别、研究决策、必需主张、缺失主张或证据字段。公共入口先重新验证 case、environment 与所有 chunk，再校验 case/environment 配对；未知或重复块引用在模型调用前早拒绝。不引入秘密盐值或加密来掩盖可枚举编号。

冻结模型中的集合字段在 Python 内部统一使用元组，阻止创建后原地修改导致哈希和校验结论失效。Pydantic 的 JSON 模式与 JSONL 持久化仍输出数组，因此磁盘数据契约不变；需要编辑时必须构造新模型，而不是修改现有实例。

## 5. 来源清单与证据池

`fixtures/sources/manifest.json` 固定以下来源：

1. 当前项目的实验合同、架构相关文档与学习材料。
2. `datawhalechina/Agent-Learning-Hub` 中与 Agent 工程、评测和知识处理直接相关的指定文件。
3. `datawhalechina/hello-agents` 中工程实践、算法、建模和评测相关的指定章节；不把前三章的概念性介绍作为主要语料。

每个外部来源必须记录仓库地址、提交 SHA、相对路径、抓取时间、内容哈希和行范围。清单只接受具体提交，不接受浮动分支。来源更新通过新增变更记录完成，不静默覆盖旧版本。

## 6. 48 条基准的构造流程

### 6.1 基础问题设计

每个基础问题先定义：用户任务、完成标准、必需主张、支持证据、允许的替代证据、错误答案风险和预期决策。问题必须能通过语料中的明确证据判定，不能依赖标注者的常识猜测。

### 6.2 环境派生

从同一基础问题派生若干环境：

- **充分**：可见知识包含完成任务所需的全部有效主张。
- **缺失**：至少一个必需主张只能从研究池取得。
- **过时**：可见池含语义相关但已失效的主张，研究池含当前证据。
- **冲突**：可见池存在互相冲突的主张，需要依据来源、版本或时效继续检索。

`visible_chunk_ids`、`research_chunk_ids`、`excluded_chunk_ids` 必须互斥。必需证据不得出现在排除池；缺失场景的缺失主张不得由可见池中的其他块完整推出。

### 6.3 标注 Agent

标注 Agent 输出结构化草稿，不输出供复核 Agent 使用的长推理过程。草稿至少包含目标决策、必需与缺失主张、证据编号、置信度和简短依据。生成参数、提示词版本、模型标识和时间写入审计集。

### 6.4 规则校验

草稿进入复核前执行确定性校验：

- 所有编号均存在且引用方向合法。
- 三类环境块互斥，环境哈希与内容一致。
- `missing_claim_ids` 是 `required_claim_ids` 的子集。
- 标签证据没有进入运行信封；关联编号不会继续进入决策模型输入。
- 过时与冲突样本包含可验证的时效或冲突关系。
- 相同规范化输入产生相同内容哈希。

规则失败的样本早拒绝，不交给复核 Agent，避免把结构错误伪装成语义争议。

### 6.5 Benchmark Reviewer Agent

独立复核 Agent 只读取基础问题、环境、证据和结构化草稿，不读取标注 Agent 的推理文本。输出：

```python
decision: Literal["approve", "revise", "reject"]
issues: list[str]
suggested_changes: list[str]
evidence_refs: list[str]
reviewer_confidence: float
```

复核重点是标签是否可由证据支持、环境是否真的改变知识条件，以及搜索决策是否与缺失或冲突事实一致。复核结果本身不能修改冻结样本，只能提出修改建议，由构造流程产生新修订版。

### 6.6 人工终审

以下样本必须人工逐条检查：

- 所有过时和冲突样本。
- 复核结果为 `revise` 或 `reject` 的样本。
- 复核置信度低于 `0.8` 的样本。
- 规则校验发现过历史错误、之后重新生成的样本。

其余 `approve` 且置信度不低于 `0.8` 的普通样本进入人工抽检池。实现只生成待审清单，不伪造人工通过状态。人工修改必须写入 `change_log.jsonl`，包含修改前后摘要、原因、操作者和时间。

## 7. 数据流

```text
固定来源清单
    ↓ 校验提交与哈希
规范化文档 → Markdown 切块 → 主张与证据映射
    ↓
基础问题 + 环境模板 → 结构化草稿
    ↓
确定性规则校验 ──失败→ 早拒绝与修订
    ↓通过
独立复核 Agent → 人工升级规则 → 人工终审/抽检
    ↓
冻结运行信封 + 标签集 + 审计集 + 整体哈希
    ↓
评测器按编号关联环境与语料
    ↓ 独立白名单
问题 + 可见知识正文 → 决策模型
    ↓
BM25 Demo 与后续 Gate/消融实验
```

## 8. 学习 Demo 与练习

本阶段 Demo 接收一个查询和一个知识环境，输出：

- 规范化查询与词项序列。
- 排名前 `k` 的块编号、总分和逐词项分数贡献。
- 必需主张的命中与缺失情况。
- 稳定的索引、环境和结果哈希。

学习材料不重复 Agent 基础概念，重点解释切块取舍、BM25 手算、环境构造、标签泄漏和复核分歧。配套 8 道练习，其中至少 2 道伪代码题；答案必须给出评分点，并能由代码、固定数据或公式核验。

## 9. 测试设计

### 9.1 单元测试

- 规范化文本与按键排序 JSON 具有稳定哈希。
- 相同文档产生完全相同的块编号、行范围和块哈希。
- 中英文、数字、标识符、空输入和标点输入的分词结果固定。
- 使用小语料手算 BM25，总分与逐项贡献在误差范围内一致。
- 空语料、空查询、未登录词和同分排序行为明确。
- 环境三集合互斥，环境哈希对集合内容变化敏感。
- 人工升级规则覆盖低置信度、过时、冲突和退回样本。
- 模型输入只含问题与可见知识正文，未知或重复可见块引用早拒绝。

### 9.2 数据测试

- 冻结集恰有 48 条，基础问题和环境类别分布符合清单。
- 每条必需主张至少有一个证据块，所有证据引用存在。
- 每条模型输入恰好解析四条可见正文，不含研究池、排除池、关联编号或类别提示。
- 运行集中不出现标签字段、目标答案或审计推理。
- 缺失、过时与冲突环境能通过对应的语义约束检查。
- 练习、答案、评分点和引用的 Demo 输出一一对应。

### 9.3 回归测试

固定小语料作为金丝雀样本。任何分词、切块或排序变化都必须显式更新预期结果和数据版本，不能通过放宽断言掩盖变化。

## 10. 与后续实验的接口

本设计为后续成对消融保留统一的 `base_question_id` 与 `environment_id`。同一基础问题可以在充分、缺失、过时和冲突环境中运行，从而分别比较：不使用知识、总是搜索、只用本地知识、使用 Sufficiency Gate 和 Oracle Gate。

搜索决策的准确率只衡量 Gate 的分类行为，不能单独证明 Harness 有效。后续实验必须同时报告任务结果、缺口识别、搜索成本和轨迹指标；本阶段只保证这些指标所需的标签和证据可追溯。

## 11. 验收标准

第二天完成需同时满足：

1. 来源清单固定到具体提交，文档、块、环境和数据集哈希可复现。
2. 48 条样本全部通过结构、引用、互斥和泄漏校验。
3. 独立复核 Agent 完成全量复核，高风险样本具备真实人工审核状态。
4. BM25 Demo 可展示词项、排名、总分、分项贡献及主张命中情况。
5. 学习材料包含 8 道练习及评分点答案，其中至少 2 道伪代码题。
6. 全量测试通过，数据变更能由审计集和变更日志追溯。

人工终审完成前，不创建 `learn-v0.1-eval-contract` 标签，也不把数据称为正式基准。

## 12. 关键取舍

- 采用确定性二元字组而非引入分词库，换取零额外模型依赖、便于手算和稳定回归；检索质量上限留给后续实验比较。
- 采用单一证据池加环境视图，显著降低构造成本，同时保留知识条件的严格控制。
- 复核 Agent 与标注 Agent 隔离，降低复述原判断造成的确认偏差；人工终审覆盖高风险样本，避免把模型一致性当作事实正确性。
- 先冻结 48 条小基准，不追求规模。当前目标是获得首组可核验实验结果，并让每个错误都能回到来源、证据和审查记录。
