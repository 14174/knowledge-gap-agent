# 阶段一可信人工门禁修复设计

## 1. 背景与目标

阶段一当前有 48 条模型复核通过的候选，其中 12 条 `outdated` 和 12 条 `conflict` 必须由人类终审。现有正式冻结逻辑重新计算了“是否需要人工”，但最终只检查 `BenchmarkCase.human_review_status`。调用方可以手工把状态改成 `approved`，冻结器无法证明结论由谁、何时、针对哪个内容版本作出。这是可信冻结漏洞。

另一个已实际暴露的问题是 `tests/benchmark/test_fixture_dataset.py` 的破坏性测试直接改写版本化夹具，再依靠 `finally` 恢复。并行测试期间，其他读取者已经读到 sentinel 和非 JSON 中间态。测试恢复成功不等于测试隔离成立。

本设计完成以下闭环：

1. 用不可变 `HumanReviewRecord` 证明人工结论，并绑定当前 `review_target_hash`。
2. 正式冻结从模型复核和人工记录重新推导状态，不信任调用方手填终态。
3. 收紧 `outdated`、`conflict` 与时间字段校验，使高风险标签具有可执行语义。
4. 所有破坏性夹具测试在 `tmp_path` 的隔离副本运行。
5. 人审清单改为“精确卡片 + 去重证据目录”，测试解析结构并与夹具逐字段比较。

本阶段不创建 `human_reviews.jsonl`，不伪造任何人工结论，不生成正式冻结文件，不创建阶段标签。

## 2. 非目标

- 不新增网页、数据库或交互式审核系统。
- 不新增 `evaluation_as_of`；过时关系完全由主张有效期和直接冲突边判定。
- 不改变运行集、标签集、审计集的物理隔离。
- 不把模型 `ReviewRecord` 与人工 `HumanReviewRecord` 合并成多态记录。
- 不自动应用人工 `revise`；内容修改、模型复核和再次人工审核仍是显式步骤。
- 不改写既有两轮 Reviewer 历史或现有 48 条模型复核记录。

## 3. 模块与职责

| 模块 | 新职责 | 明确不负责 |
| --- | --- | --- |
| `benchmark/models.py` | 定义人工结论与人工修订记录的不可变契约 | 不执行门禁，不写文件 |
| `benchmark/freeze.py` | 索引人工记录、重算人工需求、验证正式冻结资格、派生审计状态 | 不采集人工意见，不修改候选内容 |
| `benchmark/validation.py` | 校验 `outdated` 和 `conflict` 的证据拓扑及时序 | 不决定模型复核或人工结论 |
| `corpus/models.py` | 保证 `SourceDocument.fetched_at` 和 `Claim` 有效期均可比较 | 不定义基准类别 |
| `scripts/build_day2_fixtures.py` | 通过显式工作区根目录读写隔离夹具 | 不写入真实人工结论 |
| `scripts/render_stage_01_human_review_checklist.py` | 从可信夹具确定性渲染待审清单 | 不把清单空位当作正式记录 |
| `docs/阶段一人工终审清单.md` | 向人类展示精确环境和去重证据 | 不作为冻结输入 |
| `change_log.jsonl` | 追加记录人工 `revise` 被实际应用后的修改前后摘要 | 不证明人工批准 |

## 4. 数据契约

### 4.1 人工结论

在 `src/knowledge_gap_agent/benchmark/models.py` 新增：

```python
class HumanReviewDecision(StrEnum):
    APPROVED = "approved"
    REJECTED = "rejected"
    REVISE = "revise"


class HumanReviewRecord(BaseModel):
    model_config = ConfigDict(frozen=True, extra="forbid")

    schema_version: Literal["1.0"] = "1.0"
    case_id: NonEmptyString
    review_target_hash: Sha256Hex
    decision: HumanReviewDecision
    actor: NonEmptyString
    reason: NonEmptyString
    reviewed_at: datetime
    requested_changes: tuple[NonEmptyString, ...] = ()
```

约束如下：

- `case_id` 与 `actor` 去除首尾空白后不得为空；`reason` 对三种结论都必填。
- `reviewed_at` 必须包含时区，磁盘表示沿用 Pydantic ISO 8601 输出。
- `requested_changes` 不得含空字符串或重复项。
- `decision=revise` 时 `requested_changes` 至少一项。
- `approved`、`rejected` 可不填 `requested_changes`；若填写则保留为人工说明，不改变结论语义。
- 模型 `frozen=True`，集合字段使用 `tuple`，禁止额外字段。

模型复核继续使用 `ReviewRecord.decision=approve/revise/reject`；人工结论使用 `approved/rejected/revise`。两个枚举故意分开，避免模型批准被误当成人工批准。

### 4.2 人工修订日志

人工给出 `revise` 后，`HumanReviewRecord` 证明“要求修改”；真正改完内容时，`change_log.jsonl` 追加一个不可变 `HumanRevisionRecord`：

```python
class HumanRevisionRecord(BaseModel):
    model_config = ConfigDict(frozen=True, extra="forbid")

    schema_version: Literal["1.0"] = "1.0"
    record_type: Literal["human_review_revision"] = "human_review_revision"
    case_id: NonEmptyString
    actor: NonEmptyString
    reason: NonEmptyString
    before_review_target_hash: Sha256Hex
    after_review_target_hash: Sha256Hex
    before_summary: NonEmptyString
    after_summary: NonEmptyString
    changed_at: datetime
```

前后哈希必须不同，`changed_at` 必须带时区。摘要描述问题、答案键、证据关系或类别的实际改动，不能只写“已修复”。该记录不含 `human_approved`，也不改变人工结论；它只证明内容发生了什么变化。

### 4.3 时间字段

- `SourceDocument.fetched_at` 必须带时区，与 `SourceManifestEntry.fetched_at` 保持一致。
- `Claim.valid_from`、`Claim.valid_until` 只要非空就必须带时区。
- 两端均存在时继续要求 `valid_until >= valid_from`。
- 不把无时区时间自动解释为 UTC，统一早拒绝。

## 5. 冻结接口与兼容性

公共接口改为：

```python
def freeze_benchmark(
    cases: object,
    reviews: object,
    chunks: Iterable[CorpusChunk],
    claims: Iterable[Claim],
    output_dir: str | Path,
    require_human_approval: bool = True,
    *,
    human_reviews: object = (),
) -> FreezeResult:
    ...
```

`human_reviews` 是仅关键字的可选参数，放在现有参数之后。因此所有现有调用保持兼容。`require_human_approval=False` 的候选冻结继续允许没有人工记录；若候选冻结收到非空人工记录则早拒绝，避免默默丢弃安全相关输入。

内部新增 `_index_human_reviews()`，采用与模型复核相同的信任边界：先 `model_dump(mode="python")`，再用 `HumanReviewRecord.model_validate()` 重验。重复 `case_id` 在任何写盘前拒绝。

## 6. 正式冻结数据流

```text
case + environment + chunks + claims
  ├─ 重建 review_target_hash ── 校验 ReviewRecord
  ├─ requires_human_review(case, review) ── 计算 required_case_ids
  └─ HumanReviewRecord 精确集合校验
       ├─ 缺失 / 重复 / extra / stale → 早拒绝
       ├─ revise / rejected → 早拒绝
       └─ approved → 派生 human_review_status=approved
                    ↓
          生成 runtime / labels / audit
```

正式冻结规则：

1. 先完成现有 case、environment、模型复核、目标哈希和证据引用校验。
2. 用可信输入重新执行 `requires_human_review()`，得到 `required_case_ids`。
3. 人工记录的 case 集合必须与 `required_case_ids` 精确相等：
   - 少一条是 `missing`；
   - 同一 case 两条是 `duplicate`；
   - 普通样本或数据集外样本是 `extra`。
4. 每条人工记录的 `review_target_hash` 必须等于当前重算值，旧内容上的批准属于 `stale`。
5. 正式冻结只接受 `decision=approved`；`revise` 和 `rejected` 都阻断整个冻结，不静默丢样本。
6. 输入 case 的人工终态若与记录推导不一致则拒绝。非终态 `pending/not_required` 视为缓存状态，由可信记录重新派生。
7. 模型状态同样由 `ReviewRecord` 派生；矛盾的已落盘终态拒绝，允许旧的 `pending` 被派生为当前模型结论。

候选冻结不需要人工记录。它从模型记录重新派生 `review_status`，从 `requires_human_review()` 派生 `pending/not_required`，并拒绝调用方注入的人工 `approved/rejected` 终态。

输出中的 `case` 总是派生后的副本。不能把未经核对的输入状态原样写入审计文件。

## 7. 审计输出

审计行固定为：

```json
{
  "case": {},
  "review": {},
  "human_review": null
}
```

- 正式冻结且需要人工的 case：`human_review` 是完整 `HumanReviewRecord`。
- 正式冻结且不需要人工的 case：`human_review=null`。
- 候选冻结：所有行 `human_review=null`，人工状态只能是重新派生的 `pending/not_required`。
- `runtime` 和 `labels` 字段集合保持不变。
- `human_review` 进入 `audit_hash` 和最终 `dataset_hash`，不进入运行输入或标签。

## 8. `revise` 闭环

人工结论为 `revise` 时按以下顺序处理：

1. 保存原 `HumanReviewRecord`，其 `requested_changes` 是修改要求。
2. 修改 case、environment、chunk 或 claim 中对应内容。
3. 重新执行 `validate_dataset()`；失败则不得生成新复核输入。
4. 重建 `ReviewInput`，产生新的 `review_target_hash`。
5. 追加 `HumanRevisionRecord` 到 `change_log.jsonl`，记录前后哈希和具体摘要。
6. 针对新目标执行独立模型复核。
7. 若仍需人工，再生成一条绑定新哈希的 `HumanReviewRecord`。

旧人工记录永不更新或复用。由于目标哈希变化，旧 `approved` 也会被正式冻结视为 stale。

## 9. 高风险类别语义

### 9.1 `outdated`

不新增 `evaluation_as_of`。合法的 `outdated` 必须同时存在：

- 可见池中的旧主张 `old`；
- 研究池中的必需当前主张 `current`；
- `old` 与 `current` 至少一侧声明对另一侧的直接 `conflicts_with`；
- `old.valid_until` 与 `current.valid_from` 均非空且带时区；
- 严格满足 `old.valid_until < current.valid_from`。

只有“可见主张有失效时间”或“研究池存在任意必需主张”均不足以判定过时。

### 9.2 `conflict`

合法的 `conflict` 必须同时存在：

- 可见池至少一对直接冲突主张 `left/right`；
- 研究池至少一条必需主张 `adjudicator`；
- `adjudicator` 与 `left`、`right` 两端都有直接冲突边，方向可由任一侧声明。

当前 12 组受控夹具已经让裁决主张同时关联 A、B 两端，因此采用更严格的“两端关联”规则，不保留弱化分支。

## 10. 夹具构建隔离

选择显式 CLI 参数，不选择环境变量。环境变量是隐藏全局状态，容易在并行进程中串扰；`--workspace-root` 在命令行和失败日志中都可见。

接口如下：

```powershell
uv run python scripts/build_day2_fixtures.py --workspace-root <隔离根目录>
```

- 参数默认值仍是脚本解析出的仓库根目录，保留人工离线重建命令兼容性。
- `build(workspace_root: Path)` 及所有读写 helper 显式接收根目录；不得通过修改模块级 `ROOT` 切换目标。
- 测试先将 `fixtures/` 复制到 `tmp_path/workspace/fixtures/`，再传入该根目录。
- 需要注入 sentinel、删除文件、追加日志或篡改提示词的测试只能修改隔离副本。
- 测试结束后额外比较真实版本化夹具的前后哈希，证明测试没有写真实目录。

## 11. 人工终审清单

清单不再按主题筛选证据。每张卡片包含一个可解析 JSON 块，字段精确来自当前夹具：

- `case_id`、`base_question_id`、`category`、`trigger`；
- `review_target_hash`、`environment_hash`；
- 完整、有序的 `visible_chunk_ids`、`research_chunk_ids`、`excluded_chunk_ids`；
- 问题、答案键、必需主张、证据编号和缺失主张；
- 草稿中的 `draft_status`、`review_status`、`human_review_status` 缓存状态；
- 完整模型 `ReviewRecord`；
- `human_decision=null`、`human_reason=null`、`requested_changes=[]`。

卡片之后建立去重证据目录。所有卡片三池出现过的 chunk 恰出现一次，每项包含：

- 完整 `chunk_id`、`text`、`source_id`、`heading_path`、`start_line`、`end_line`、`claim_ids`；
- 每条关联 claim 的 `statement`、`evidence_chunk_ids`、`valid_from`、`valid_until`、`conflicts_with`。

新增轻量渲染脚本从夹具确定性生成文档。测试使用独立解析器读取卡片和证据目录，与 `human_review_queue.jsonl`、`review_inputs.jsonl`、`reviews.jsonl`、`drafts.jsonl`、`chunks.jsonl`、`claims.jsonl` 做结构化精确比较；不再用关键词是否散落在正文作为主要断言。

## 12. 错误处理与原子性

所有以下错误必须发生在创建输出目录或正式文件之前：

- 人工记录模型不合法、时间无时区；
- 人工记录 missing、duplicate、extra；
- 人工记录目标哈希 stale；
- 人工结论为 `revise/rejected`；
- case 中已有终态与可信记录矛盾；
- `outdated/conflict` 证据拓扑不满足新规则；
- 构建器隔离根目录缺少必要夹具。

通过全部校验后继续使用现有临时文件、硬链接提交、锁文件和回滚机制。不得为人工记录另写一套非原子的输出流程。

## 13. 测试策略

1. **模型测试：** 三种人工结论、`revise` 必填修改、时区、不可变、额外字段、集合元组；来源和主张拒绝无时区。
2. **规则测试：** `outdated` 缺少任一时间、非严格时间顺序、无直接冲突均失败；`conflict` 缺少可见冲突或裁决只连接一端均失败。
3. **冻结测试：** 覆盖 missing、duplicate、extra、stale、revise、rejected、伪造 case 状态、普通 case null 审计、候选兼容、无写盘副作用。
4. **夹具测试：** 当前 12+12 高风险样本满足收紧规则；所有破坏性重建在 `tmp_path`；真实夹具哈希不变。
5. **清单测试：** 24 张卡片一一对应；三池数组顺序精确；模型记录精确；证据目录去重且字段完整；人工字段为空。
6. **回归验证：** 两个 Demo、学习测试、全量测试、`uv lock --check`、`git diff --check`。

`docs/experiments.md` 只在实际运行后记录真实命令和结果。测试不得硬编码全量 `passed/skipped` 数字。当前“无正式冻结文件、无阶段标签”的断言是阶段性门禁；真实人工批准并发布时必须同步删除或改写该断言，不能成为永久产品约束。

## 15. 关键取舍

- **独立记录而非给 `ReviewRecord` 加字段：** 防止模型身份与人类身份混淆。
- **绑定 `review_target_hash` 而非 `case_id`：** 编号稳定不代表内容未变。
- **正式冻结要求人工记录集合精确相等：** 多余记录可能来自错误数据集，不能静默忽略。
- **候选冻结拒绝非空人工记录：** 候选产物不消费人工批准，显式失败比静默丢弃安全。
- **状态派生而非删除状态字段：** 保持现有 JSON 契约兼容，同时把字段降为可验证缓存。
- **显式 `--workspace-root`：** 比环境变量更易审计、可并行、失败日志更清晰。
- **清单采用结构化卡片和去重目录：** 同时满足人工阅读和机器精确核对，避免复制 24 份证据全文。

## 16. 验收条件

- 任意伪造 `human_review_status=approved` 均不能绕过正式冻结。
- 只有绑定当前哈希、集合精确、结论为 `approved` 的人工记录才能放行必审 case。
- 当前仓库仍不存在人工记录文件、正式冻结文件和阶段标签。
- 收紧后的 12 条 `outdated` 与 12 条 `conflict` 全部通过，构造出的弱反例全部失败。
- 所有破坏性夹具测试只修改隔离目录，并证明真实夹具字节不变。
- 清单卡片、三池、模型复核和去重证据目录与真实夹具结构化精确相等。
- 全量验证通过后才更新实验数字；24 条人工终审仍保持 `pending`。
