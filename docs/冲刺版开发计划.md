# 10 天冲刺版开发计划

> 目标：在 10 天内交付一组能写入简历、可复跑且能追溯到原始 Trace 的首轮实验结果，并把五个实现阶段整理成可供其他学习者复现的渐进式课程。范围收敛为单智能体知识研究闭环；不把多智能体、跨模型大规模消融、自动发布 Skill 或课程平台开发放进本轮验收。

## 1. 交付判断

本轮不是做一个功能堆叠的聊天应用，而是完成三个可检验主张：

1. Runtime 能在固定配置下完成工具调用、终止、Trace 记录和确定性 Replay。
2. Agent 能区分本地知识的 `enough`、`partial`、`missing`，只在知识不足时研究外部证据。
3. 第一轮任务沉淀的已验证知识，能在第二轮相近但不相同的任务中被实际命中，并减少不必要搜索。

Skill Evolution 只完成 Candidate 与 Gate 演示：从失败分类或成功 Trace 提炼候选步骤，在独立任务集比较收益和回归；本轮不允许它自动进入默认运行时。

### 1.1 取舍与边界

| 本轮实现 | 本轮不实现 | 原因 |
|---|---|---|
| 单 Research Agent、两个工具、SQLite 知识库、固定语料、Web 研究适配器 | 多智能体编排 | 没有稳定单智能体基线就无法解释协调成本与收益 |
| `KnowledgeProvider` 接口与本地实现 | 绑定某个 LLM Wiki 产品 | 先固定实验变量；后续适配器不应改变 Runtime |
| 结构化充分性判断、证据 Gate、写回 | 训练充分性分类器 | 训练集与标注规模不足，第一版用可审计的结构化输出 |
| Candidate Skill、离线 Gate、版本记录 | 自动 Promotion | 防止少量 Trace 过拟合或污染全局行为 |

固定语料是严谨性的前提。评测用 `fixtures/corpus/` 中冻结的来源快照，并保存 URL、抓取日期和内容哈希；真实 Web Search 只用于独立的现场演示，不与首轮主结果混在一起。

## 2. 首轮实验设计

### 2.1 数据与分割

制作 48 条可审计任务，按任务和知识覆盖情况标注，不使用模型自行生成 Ground Truth：

| 分组 | 数量 | 本地知识状态 | 主测问题 |
|---|---:|---|---|
| 本地充分 | 12 | 所有必需 Claim 已覆盖且未过期 | 是否避免无意义搜索 |
| 本地部分覆盖 | 12 | 缺少至少一个必需 Claim | 是否定位缺口并补证 |
| 本地缺失 | 8 | 无可用本地证据 | 是否触发研究 |
| 已过期或冲突 | 8 | 证据过期或 Claim 冲突 | 是否拒绝直接作答 |
| 重复知识第二轮 | 8 | 与第一轮主题相关但问题不同 | 是否命中写回知识 |

每条样本保存 `required_claims`、`local_knowledge_ids`、`need_research`、允许来源、正确答案要点和人工标注理由。前 40 条用于 E0/E1/E2 的主对照；最后 8 条只用于写回后的知识复用实验。Skill 的目标集与回归集从前 40 条中按主题隔离，不能把用于提炼的 Trace 放入测试集。

### 2.2 对照组与可复现配置

| 变体 | 唯一变化 | 目的 |
|---|---|---|
| E0 | 最小 ReAct + 研究工具 | 建立质量、步骤、搜索和成本基线 |
| E1 | E0 + 长期知识检索 | 测量已有知识是否可减少搜索 |
| E2 | E1 + Knowledge Sufficiency Gate | 测量按缺口研究是否优于固定检索策略 |
| E3 | E2 + Evidence Verification + Write Gate | 测量写回的可靠性和第二轮复用 |

每次运行固定模型版本、系统提示词哈希、温度、最大步数、工具版本、数据集版本和语料哈希。每个变体跑 3 次；若成本不足以支持 3 次，报告必须标注为单次试验，只给出观测值而不写统计结论。

### 2.3 指标与公式

充分性标签中，把 `partial` 与 `missing` 合并为“需要研究”。

```text
Precision = TP / (TP + FP)
Recall    = TP / (TP + FN)
F1        = 2 × Precision × Recall / (Precision + Recall)
FalseSufficientRate = FN / N_need_research
TaskSuccess = N_passed / N_total
KnowledgeReuseRate = N_runs_with_actual_knowledge_hit / N_reuse_eligible
RepeatedSearchReduction = 1 - SearchCalls_E3 / SearchCalls_without_write_back
SkillGain = Score_with_candidate - Score_without_skill
RegressionRate = N_regressed_on_holdout / N_holdout
```

`FalseSufficientRate` 必须单列，因为它会让系统在知识不足时过早停止。质量指标至少包括任务通过率和 Citation Coverage；效率指标至少包括每任务搜索次数、输入 Token、延迟和步骤数。对 E0、E1、E2 的同题结果采用配对差值，并对任务维度做 1,000 次 bootstrap，报告均值差及 95% 置信区间。若样本量与时间不足，不把区间跨零的结果描述为“提升”。

### 2.4 最小算法实现

1. 检索：SQLite FTS 或 BM25。对查询 q 与文档 d，保存 `score(q,d)`，其核心项为：

```text
BM25(q,d) = Σ IDF(t) × f(t,d) × (k1 + 1)
            / (f(t,d) + k1 × (1 - b + b × |d| / avgdl))
```

首版取 `k1 = 1.5`、`b = 0.75`，把参数写入配置。语义向量检索留作后续消融，避免第一轮同时改变检索模型和知识判断机制。

2. 充分性判断：模型只输出受 schema 约束的 `label`、`missing_claims`、`stale_ids`、`conflict_ids`、`confidence` 和 `reason`。判定输入必须是任务所需 Claim 与检索证据摘要，不能只根据相似度分数。
3. 证据 Gate：每条 Candidate Knowledge 必须通过来源类型、Claim-Evidence 对齐、时效、去重和冲突检查。未通过项保存失败理由，不写入 Active Knowledge。
4. 技能门禁：Candidate 需要在目标集不低于基线、独立回归集不超过事先冻结的阈值、成本变化可解释且来源 Trace 完整时才显示“可发布”。本冲刺中该状态只用于报告，不改变默认策略。

## 3. 10 天排期

每天结束前必须有可运行命令、一次固定输入输出和当天文档。第 2、4、6、8、10 天为阶段检查点，下面列出的 Demo 可录屏、截图或保存终端输出。

### 阶段一：实验合同与数据底座（第 1–2 天）

| 天数 | 实现与学习重点 | 当日产出文档 | 学习 Demo 与验收 |
|---|---|---|---|
| 第 1 天 | 建立目录、依赖锁定、`RunConfig`、Trace schema、48 条任务的标注格式；学习评测章节中“固定任务集、轨迹指标、失败分类”的做法 | `docs/实验合同.md`：变量冻结表、样本 schema、指标定义、运行命令 | `demo/01_config_trace.py`：同一配置生成相同 `config_hash`；输出一条合法 Trace JSON |
| 第 2 天 | 完成冻结语料、来源元数据、内容哈希和人工 Claim 标注；学习检索的分块、倒排索引与 BM25 | `docs/基准数据说明.md`：样本分布、标注准则、语料来源、数据泄漏检查表 | `demo/02_bm25_retrieval.py`：给定查询输出 top-k、BM25 分数、命中文档及必需 Claim 覆盖情况 |

阶段验收：任意样本都能追到 required claims、可用证据和标注人理由；数据集、语料和配置均有哈希。

### 阶段二：最小 Runtime 与 E0 基线（第 3–4 天）

| 天数 | 实现与学习重点 | 当日产出文档 | 学习 Demo 与验收 |
|---|---|---|---|
| 第 3 天 | 实现 `State → Action → Observation → State`、工具 schema 校验、`max_steps`、超时、错误分类；参考经典 Agent 范式与自研框架章节，只实现 ReAct | `docs/运行时状态机.md`：状态转换表、终止条件、错误分类、工具接口 | `demo/03_react_loop.py`：计算或查证任务完整展示动作序列；重复动作与工具错误均会终止或恢复 |
| 第 4 天 | 实现 Trace Store、Checkpoint、Replay；运行 E0 的 3 次固定配置实验 | `docs/E0基线报告.md`：任务通过率、搜索次数、Token、延迟、失败 taxonomy 和原始运行索引 | `demo/04_trace_replay.py`：用已保存 Observation 离线 Replay，不再发起模型或搜索调用 |

阶段验收：E0 的每个结果都可定位到 `run_id`、配置、Trace 与原始 Observation；不通过的样本有明确失败标签。

### 阶段三：长期知识与充分性 Gate（第 5–6 天）

| 天数 | 实现与学习重点 | 当日产出文档 | 学习 Demo 与验收 |
|---|---|---|---|
| 第 5 天 | 定义 `KnowledgeProvider`，完成 SQLite/BM25 实现与 E1；学习记忆、检索和长期/短期状态分离 | `docs/知识存储与检索.md`：Entry schema、索引参数、Provider 边界、E0/E1 对照 | `demo/05_knowledge_provider.py`：同一任务展示无知识与有知识的检索上下文、实际命中 ID 和搜索决策 |
| 第 6 天 | 完成结构化 Sufficiency Evaluator 与 E2；学习上下文工程中证据选择和 Token budget 的最小做法 | `docs/知识充分性实验.md`：判断 schema、混淆矩阵、F1、FalseSufficientRate、典型误判 | `demo/06_sufficiency_gate.py`：分别演示 `enough`、`partial`、`missing` 三种输入及缺口驱动的下一步 |

阶段验收：E2 不得只输出标签，必须给出缺失 Claim 或过期/冲突证据 ID。门槛在运行 E2 前冻结，不能根据结果临时修改。

### 阶段四：证据写回与知识复用（第 7–8 天）

| 天数 | 实现与学习重点 | 当日产出文档 | 学习 Demo 与验收 |
|---|---|---|---|
| 第 7 天 | 实现 Research Plan、Evidence Item、Verification 与 Candidate Knowledge；学习深度研究案例的来源筛选和引用归因 | `docs/证据验证与写回门禁.md`：Evidence schema、Gate 规则、拒绝案例、知识版本关系 | `demo/07_evidence_gate.py`：一条证据因过期或 Claim 不匹配被拒绝，另一条通过后成为 Candidate Knowledge |
| 第 8 天 | 完成 E3：第一轮研究写回，第二轮相关任务复用；计算实际命中 ID 与搜索削减 | `docs/知识复用实验报告.md`：无写回/E3 的配对表、Reuse Rate、RepeatedSearchReduction、质量检查 | `demo/08_round_trip_reuse.py`：展示“研究→验证→写回→相关任务命中→可选搜索”的完整闭环 |

阶段验收：第二轮任务必须与第一轮不同；只有 Trace 记录命中新增 Knowledge ID 才计为复用。

### 阶段五：候选技能、统计报告与简历证据（第 9–10 天）

| 天数 | 实现与学习重点 | 当日产出文档 | 学习 Demo 与验收 |
|---|---|---|---|
| 第 9 天 | 从稳定失败或成功 Trace 生成 1–2 个 Candidate Skill，执行目标集和回归集；学习 Skills 与评测章节的版本、适用范围和回归检查 | `docs/候选技能门禁报告.md`：来源 Trace、适用范围、目标集差值、回归集、成本变化与 Gate 决策 | `demo/09_candidate_skill_gate.py`：一个候选因回归被拒绝；另一个即使通过也只标为 `validated` |
| 第 10 天 | 汇总 E0–E3、生成配对统计和失败案例；复跑一条全链路命令，整理简历证据 | `docs/首轮实验总报告.md` 与 `docs/简历证据卡.md`：结果表、置信区间、限制、可使用的简历表述、复现步骤 | `demo/10_reproduce_report.py`：从版本化数据、配置和 Trace 生成总表；新机器按 README 可复跑 |

阶段验收：总报告只使用运行产物中的真实数字；没有 3 次重复或配置不全的指标保留 `TBD`。简历证据卡必须能回链到表格、Trace 和命令。

## 4. 学习材料映射

本计划不安排 Hello-Agents 第 1–3 章。每阶段只读能直接落到当前提交与 Demo 的部分：第 4 章的 ReAct/Plan-and-Solve 实现、第 7 章的框架构建、第 8 章的记忆与检索、第 9 章的上下文工程、第 12 章的评测和第 14 章的深度研究案例。[Hello-Agents 目录](https://github.com/datawhalechina/hello-agents)

Agent Learning Hub 的路线与本轮一致：最小 Agent Loop、工具与记忆、研究一个现代 Harness、Skills、评测与可观测性。这里选其中的 Runtime、检索、Trace、Skill Gate 和 Eval，不学习以角色划分为主的多智能体模板。[Agent Learning Hub](https://github.com/datawhalechina/Agent-Learning-Hub)

每个 Demo 固定采用“输入 → 中间状态/Trace → 输出 → 指标或断言”四段结构。Demo 不只展示成功路径，还必须包含一个失败或拒绝样本；否则它不能证明 Gate 和恢复逻辑生效。

### 4.1 渐进式学习产物

每个两天阶段同步形成一个 `learning/stage-*` 学习单元，包含工程讲解、动手实验、练习和独立答案。课程面向会 Python、调用过大模型接口但没有实现过 Agent 的开发者，跳过智能体历史与语言模型基础。

每阶段创建一个 Git 标签固定可运行快照：

```text
learn-v0.1-eval-contract
learn-v0.2-react-runtime
learn-v0.3-knowledge-gap
learn-v0.4-knowledge-evolution
learn-v0.5-skill-gate
```

每阶段默认包含 3 道简答题、2 道伪代码题、1 道 Trace 分析题、1 道实验设计题和 1 道代码修改题。答案文件按“提示、参考答案、评分点、常见错误”组织，供学习者先独立作答，再让 AI 根据 Trace 和评分点反馈。详细契约见 [渐进式学习课程设计](superpowers/specs/2026-09-21-渐进式学习课程设计.md)。

## 5. 最终卖点与可写入简历的条件

| 可主张卖点 | 必须具备的证据 | 未达到时的表述 |
|---|---|---|
| 知识缺口驱动研究 | E2 混淆矩阵、F1、FalseSufficientRate、E0/E2 质量与搜索对照 | “实现了可审计的知识充分性判断原型” |
| 经验证的长期知识复用 | E3 第二轮任务的实际命中 ID、Search Reduction、质量对照 | “实现了带证据 Gate 的知识写回流程” |
| 可复现 Agent Harness | 固定配置、Trace、Replay、失败分类、单命令报告 | “实现了带 Trace/Replay 的单智能体运行时” |
| 安全的 Skill Evolution | Candidate 来源、目标集、回归集、Gate 决策、版本记录 | “实现了候选技能的离线评测门禁” |

最终简历只选 3–4 个真实指标：Task Success、Sufficiency F1、Search Calls 或 RepeatedSearchReduction、KnowledgeReuseRate。若 Candidate Skill 只做完演示，不把它写成“自进化已提升任务成功率”。

## 6. 风险、降级与每日决策

| 风险 | 处理方式 | 不可妥协项 |
|---|---|---|
| 第 2 天数据标注未完成 | 将主集压缩至 24 条，保持四种知识状态齐全 | 不能用无 Ground Truth 的样本报告 F1 |
| 模型或外部搜索不稳定 | 主实验完全使用冻结语料；现场 Web Demo 单列 | 不能把线上波动混进对照数据 |
| API 成本超预算 | 优先保留 E0/E2/E3 与每变体 3 次；E1 只跑一次探索性结果 | 不能把单次运行伪装成稳定增益 |
| LLM Wiki 接入拖期 | 保持 `KnowledgeProvider` 不变，用 SQLite/BM25 完成对照 | 不为接一个后端牺牲实验可复现性 |
| Skill 样本太少 | 只报告被 Gate 拒绝或“待更多 Trace”，不发布 | 不能为了完整故事绕过回归集 |

每天最后 30 分钟更新实验日志：完成项、运行命令、数据/配置哈希、失败样本、次日唯一阻塞项。第 4、6、8、10 天若阶段验收未通过，暂停新增功能，先修复可复现性或标注问题。
