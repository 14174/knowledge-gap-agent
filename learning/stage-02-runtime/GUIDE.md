## 一条调用链读懂控制流

```text
TaskInput + RunConfig
 → run_task 核对提示词和客户端配置
 → ModelClient.complete
 → parse_action
 → research：执行工具、保存 Observation、进入下一步
 → answer：核对引用、保存答案、停止
 → save_run
 → replay_run 用保存响应重新执行同一状态机
```

按顺序读：

1. [模型与输入](../../src/knowledge_gap_agent/runtime/models.py)：`TaskInput` 只有问题与知识，`EvidenceView` 用正文摘要防止意外更改，`Action` 验证研究和作答的不同字段。
2. [循环](../../src/knowledge_gap_agent/runtime/loop.py)：`run_task` 先重验模型、核对配置，再创建运行身份；每步保存请求、响应、动作与观察。
3. [模型适配器](../../src/knowledge_gap_agent/runtime/model.py)：`MessagesClient.complete` 将温度、模型、超时、输出上限和重试发到真实 HTTP 请求，保留返回的实际模型和用量。
4. [轨迹存储](../../src/knowledge_gap_agent/tracing/store.py)：`save_run` 独占创建，`replay_run` 从原始响应重走循环并比较行为。

本阶段不读答案标签，不判断证据语义是否支持结论，也不负责长期知识写回。这些在后两阶段实现。标签评分由阶段五的评测器承担。

## 状态和字段的生命周期

任务身份是完整输入的规范 JSON 摘要；同样输入可有同样任务身份。每次运行另有随机运行身份，因此能保存重复试验。评测器还需要“样本、变体、重复序号”的关联键，因为不同环境可能给无知识基线产生相同任务输入。

`calls` 保存每次模型调用，包括失败和重试；`observations` 保存实际工具结果；`events` 使用既有开始、动作、工具完成、结束四种事件。`answer` 只在合法作答时产生。失败停止不是空字符串答案，也不能从失败中猜一个成功结果。

提示词必须满足：

```text
prompt_hash = SHA256(system_prompt 的 UTF-8 原始字节)
task_id = SHA256(规范 JSON(TaskInput))
模型传输尝试次数上界 = retry_limit + 1
```

最后一式只描述模型传输重试，不表示工具业务失败会自动重试。网络 socket 超时也不是所有重试共享的总运行期限。

## 成功与失败怎样体现在轨迹

成功例：开始 → 研究动作 → 工具观察 → 作答动作 → 成功结束，共五个事件。下一步模型看到上一轮真正返回的正文和引用；答案只能引用已看到的编号。

重复查询例：开始 → 研究 → 工具观察 → 相同规范查询 → 失败结束，停止原因为 `repeated_query`。规范化处理 Unicode、大小写和空白，防止用格式变化绕过重复检查。工具异常或超时会保存失败观察后停止，未知引文会得到 `invalid_citation`。

同步工具由线程执行。等待超时能让循环返回，但不能强制终止已经开始的工作线程；真实工具本身必须有底层超时。本阶段不提供逐步自动断点恢复。

## 为什么重放仍要运行状态机

只读取保存的最终答案，无法发现动作顺序、观察引用或停止原因被改坏。重放先验证完整内容摘要，然后使用已保存模型响应和工具观察再次调用循环，比较输入、配置、调用载荷、事件、观察与最终结果。它忽略新生成的运行身份和耗时，因为这些不是离线行为一致性的一部分。

内容摘要用于发现意外篡改；它不是数字签名，不能抵抗恶意程序修改正文后重新计算摘要。重放也不能证明远端模型再次调用会给同样答案。

## 教程联系与验收

固定教程第七章的消息与历史管理帮助理解“每次调用需要显式上下文”；本项目把它落实为 `make_payload` 中的问题、知识、动作与观察。项目阶梯要求每一步都有可运行作品，本阶段的作品就是两种入口都能运行的循环和离线重放。课程不展开框架历史。

验收时，用一句话复述：一次研究结果如何进入下一次模型请求，最后为什么允许引用它？再运行本页三个命令，并解释 `answered` 与任一失败停止原因的区别。
